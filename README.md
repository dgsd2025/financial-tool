# 财务中心 · yc-finance-web

星逸平台第 9 个系统。一期范围：**系统整体结构 + 工具箱（T2 银行流水转凭证、T4 日损益速算表）**。

---

## 快速启动

```bash
cd yc-finance-web
node server.js 5190
```

打开 http://localhost:5190

> 端口说明：5173 / 5180 / 5181 已被其他系统占用，默认改用 **5190**。
> 也可以不启服务器，直接双击 `index.html` 打开——所有功能都在浏览器端运行。

**零依赖**：不需要 `npm install`，没有构建步骤，只用 Node 内置模块。

## T2 的设计要点

### 支持格式
`.xlsx` / `.csv` / `.tsv` / `.txt`，UTF-8 与 **GBK 自动识别**（国内网银导出常见 GBK）。

xlsx 解析用浏览器内置的 `DecompressionStream` 实现 ZIP 解压，**不依赖任何第三方库**。

### 自动识别
- **表头定位**：银行流水前几行常是账号、户名等说明，工具扫描前 12 行按关键词密度自动定位真正的表头
- **列映射**：10 个字段各有别名表（如日期 = 交易日期 / 记账日期 / 业务日期…），自动匹配后可人工调整
- **金额形态**：支持「收入/支出双列」「发生额 + 借贷标志」「带正负号金额」三种

### 匹配规则

匹配**只看摘要**。对方户名容易误命中——例如「交通运输部」含「运输」会错配到物流费规则——所以对方户名必须由规则显式声明 `scope: 'both'` 才纳入匹配范围。

界面上每笔都显示「**匹配依据**」列，写明是靠摘要还是对方户名命中的。

### 不猜
匹配不上的一律进例外清单，**绝不猜科目**。例外可逐条人工指定，并勾选「存为规则」沉淀进规则库——**用得越久越准**。

### 输出
- **凭证导入 CSV**：15 列（日期·凭证字·凭证号·摘要·科目编码·科目名称·借方·贷方·主体·业务线·项目·合同号·对方户名·流水号·账号），自动校验借贷平衡
- **例外清单 CSV**：未匹配的单独导出，人工在账务系统处理

### 合规提示内置
主体间调拨命中时会打出警告「主体间调拨须走专用审批流」——这是方案里的最高风险项（未清账导致税务注销困难），在工具层就提示。

## T4 日损益速算表的设计要点

### 三层结构（原生支持，不拍平）

```
第 3 层  事业部汇总   = 天猫 + 特卖平台 + 快手 + 私域
第 2 层  特卖汇总     = 京东自营 + 唯品会 + 京东POP
第 1 层  6 个渠道子表  ← 只有这层需要数据源
```

**第 2、3 层由工具按渠道结构重新聚合，不接受导入、不用跨表引用。**
旧 Excel 在这两层用跨表公式，私域列整体串行 7 行，算出「房租物业水电-公摊 = -659.18 元」的负房租。

### 核心约束：不对齐就禁用汇总

任意两个渠道的取数天数差 > **2 天**时，**禁止生成第 2、3 层汇总**，只允许看单渠道。

理由：六个渠道实际取数天数从 0 到 23 天不等，`SUMIFS` 会把「22 天的私域」和「1 天的天猫」直接相加——数字算得出来，但没有业务含义。**拿去开经营会比没有数更危险。**

导出的 CSV 里，汇总行会写明「已禁用：渠道取数天数不对齐，极差 N 天」，而不是给一个错的数。

### 硬推口径显式标注

京东自营零售成本无数据源，按 `收入 × 45%` 硬推，退货按 `-16%` 硬推——所以它的毛利率是**设定值不是算出来的**。

工具在渠道列表、日损益表、导出文件里都标「含硬推」，日历格子也用红色区分。Excel 里「算出来的」和「设定的」长得一样，这是最容易在经营会上被误读的地方。

### 留空 ≠ 0

- **留空** = 当天没数据，不计入天数，不进汇总
- **0** = 当天确实为零，计入天数

这个区分直接决定汇总能不能用，手工录入界面里有明确提示。

### 工具消化掉的结构差异

| 差异 | 旧 Excel | 本工具 |
|---|---|---|
| 日期列偏移 | 天猫 K 列、京东自营 I 列、私域 E 列，步长还不同 | 内部处理，用户不用记 |
| 行号差异 | 天猫推广费拆多行，京东自营只有第 14 行一行 | 按字段名对齐 |
| 汇总方式 | 跨表公式引用，易串行 | 按渠道结构重新聚合 |
| 缺行处理 | 悄悄取到隔壁行的数 | 直接报「缺某行」 |

### 取数口径

| 渠道 | 项目 | 规则 |
|---|---|---|
| 天猫 | 收入 | 销售单明细账 → **只取「天猫-澳乐旗舰店」**，排除 zzzrest |
| 天猫 | 直通车 | 按**记账时间**归属，不按消耗日 |
| 天猫 | CPS | 按明细表日期列归属 |
| 京东自营 | 收入 | 收入交易概况 → 当日成交金额 |
| 京东自营 | 推广费 | 京准通 → 当日支出金额，**源表为负数需取绝对值** |
| 京东自营 | 成本 / 退货 | **硬推 45% / -16%** |

有源文件的只有天猫和京东自营，其余四个渠道手工录入。

## 实测结果

用 `示例文件/银行流水_示例.csv`（18 笔，含 2 行说明抬头）：

| 项 | 结果 |
|---|---|
| 表头定位 | 自动跳过 2 行说明，命中第 3 行 |
| 列映射 | 8 个字段全部自动识别 |
| 匹配 | 15 / 18 = **83%** |
| 例外 | 3 笔（结息金额为 0、ETC通行费无规则、不明款项） |
| 凭证 | 15 张 / 30 行，**借贷平衡** |

例外的 3 笔都判断正确——工具没有硬猜。

## 数据与安全

- **所有解析在浏览器端完成，文件不上传任何服务器**
- 规则库与处理记录存在浏览器 `localStorage`
- 服务器只做静态文件分发，不接收、不存储任何业务数据

> ⚠️ localStorage 是浏览器本地存储，换电脑/清缓存会丢。接入平台后应改为服务端存储——这也是接入时要做的第一件事。

## 下一步

按「跑完一个再做下一个」的原则：

1. **让出纳用 T2 跑一次真实的月度流水**，让会计用 T4 补一个月的真实渠道数据
2. 观察 T2 真实匹配率，把例外沉淀成规则；观察 T4 能不能把六渠道补到对齐
3. 两个都用顺了，再开 **T3 对账单核对器**

真实数据跑一遍会暴露示例覆盖不到的问题：各家银行的导出格式差异、摘要写法习惯、各渠道源文件的实际结构。**这些正是规则库要吃进去的东西。**

> T4 的第一次使用大概率会卡在「补不齐六个渠道」——那不是工具的问题，是数据源本身就缺。
> 工具的价值恰恰在于**把这件事明确暴露出来**，而不是像 Excel 那样给一个看起来能用的错数。
